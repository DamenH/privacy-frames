# Resource path resolution audit

The recorded `colon-resource.json` is historical evidence from before the fix, with source and build hashes. `colon-resource.ts` reproduces that behavior only against that earlier build; it intentionally fails against the fixed runtime. It uses localhost ports 4210, 4211 and 4219, creates a temporary self-signed TLS receiver, and overwrites the evidence file if it succeeds. The browser accepts the test certificate for receiver calibration only. The post-fix end-to-end check is `node test/resource-paths.ts` after building the runtime, manager and installer.

A real local publisher serves a same-scope resource named `https:127.0.0.1:<port>`. The ordinary installation UI, supplied with that resource URL, stores that path. On the HTTP runtime, the actual `resourceURL` resolves it to a different HTTPS origin. The opposite protocol combination matters for the deployed HTTPS runtime: an `http:` first segment can escape to HTTP. This is a URL-resolution counterexample, not an observed information leak.

Chromium 153 and Firefox 155 both install the fixture, then display the startup error without running its publisher script. The same publisher runs normally when the additional resource is omitted. In each browser a native request reaches the independent receiver, while the receiver observes no request during the failed launch. The document response carries `connect-src 'self'`; no relevant service worker event was observed. Because the publisher script did not run, this does not test CSP or the worker as a defense against an executed exfiltration request. Chromium's console identifies `Document resource leaves its application`; Firefox reports a generic error. The root guard parses all resource aliases using `parseInstalledDocument` and `parseWindowContentMetadata`, whose alias validation rejects targets outside the application URL. The observation and code path explain the fail-closed launch; they do not establish a complete browser-channel guarantee.

The normal installer sets the source entry path to `index.html`. Other captured paths, including potential worker resources, are included in the root document's aliases, which are validated before publisher code starts; therefore this particular normal launch cannot create a worker first. The same applies to the entry in an admitted payload based on the root guard's all-resources validation, but a forged entry and alternate worker bootstrap were not separately exercised. Nested document bootstrap also parses aliases through `parseDocumentBootstrap`. This is code inspection, not exhaustive reachability analysis.

The fix resolves every resource path as a relative reference, preserving scheme-like filenames. Admission additionally requires each canonical URL to stay within the slash-terminated application base and rejects duplicate canonical URLs. The existing startup alias validation remains. Admission tests cover both scheme-like names, a scheme-like entry, nested paths, a collision and an escape caused by URL normalization of control characters in forged admission payloads. The end-to-end test uses the ordinary installer and starts the app in Chromium and Firefox with a colon-named and a nested resource. Raw control-character paths are not described as normal installer inputs: URL parsing can encode or normalize them before capture.

The installer checks raw paths for duplication and falls back to a hash-based path when it encounters an unsafe path. It derives same-scope paths from canonical URL pathnames, where control characters and other problematic bytes are normalized or percent-encoded before `safePath`; percent-encoded paths use the fallback. Admission remains the authoritative canonical containment and collision check for any received payload. The installer has not been changed to silently rename a canonical collision that might somehow reach it; such an installation is refused.
